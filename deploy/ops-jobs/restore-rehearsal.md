# 백업 복구 리허설 체크리스트 (③)

> 목적: 복구를 **실제로 해보고** RPO/RTO 를 숫자로 확정한다.
> 백업 존재 ≠ 복구 가능. 월 1회 리허설로 이 간극을 닫는다.

## 목표치 (먼저 합의해서 채우기)

| 지표 | 정의 | 목표 | 최근 측정 |
|---|---|---|---|
| RPO | 장애 시 잃어도 되는 데이터 시간(백업 주기) | 예: ≤ 24h | ______ |
| RTO | 복구에 걸리는 시간 | 예: ≤ 1h | ______ |

## 대상 범위

- [ ] **DB(운영=Supabase)**: 콘솔 PITR 로 특정 시점 복원 1회 검증
- [ ] **DB(스테이징/로컬)**: `restore-rehearsal.sh` 로 최신 덤프 복구 + 스모크
- [ ] **Storage(이미지)**: 버전ing/휴지통 정책 확인, 삭제 후 복원 테스트
- [ ] **설정**: `.env` / `.env.images` 백업본으로 재기동 가능한지(암호화 보관)

## 월간 리허설 절차

1. 최신 백업 확인(`pg_backup.sh` 산출물 신선도 = RPO).
2. 스테이징에서 `ENV=staging BACKUP_DIR=… ./restore-rehearsal.sh` 실행.
3. 스모크 쿼리 통과 확인(예: `select count(*) from jobs;`).
4. RPO/RTO 를 위 표에 기록, 목표 대비 편차 있으면 원인/조치 메모.
5. Supabase PITR 로 임의 시점 복원 1회(운영 데이터 손대지 않는 복제/새 프로젝트에서).
6. 담당자 서명·날짜 기록.

## 실패 시

- 복구 실패 = 백업 무효. 즉시 백업 파이프라인 점검(형식/권한/보관주기).
- 부분 복구만 되면 스키마/확장/시퀀스 누락 여부 확인.
