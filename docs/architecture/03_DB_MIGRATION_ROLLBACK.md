# DB 마이그레이션 · 롤백 정책 (P0)

> 핵심 한 줄: **코드 롤백 ≠ 스키마 롤백.**
> 이미지를 v1 로 되돌려도 스키마는 v2 그대로 남는다. 그래서 스키마는
> **앞으로만(expand-only)**, 그리고 **하위호환**으로만 바꾼다.

## 왜 이 규칙인가

배포는 "이미지 태그 교체 → 헬스체크 실패 시 이전 태그로 롤백"이다(`deploy.sh`).
그런데 마이그레이션은 자동으로 되돌아오지 않는다.

```
v1 코드 ──(migrate)──> v2 스키마 ──> v2 코드 배포
                                   │ v2 불량 → 이미지만 v1 로 롤백
                                   ▼
              v1 코드가 v2 스키마와 만남
```

만약 v2 마이그레이션이 **파괴적**(컬럼 rename/삭제, NOT NULL 추가, 타입 변경)이면
롤백된 v1 코드가 없는 컬럼/제약과 충돌 → 크래시 루프 → 헬스체크 실패.
`deploy.sh` 는 "이미지 롤백 성공"이라고 보고하지만 서비스는 계속 다운된다.

## 허용 규칙 — expand-contract

스키마 변경은 **여러 배포에 걸쳐 단계로** 나눈다. 한 배포는 항상 하위호환.

1. **Expand(추가)** — 새 컬럼/테이블/인덱스를 **nullable 또는 기본값**으로 추가.
   구버전 코드도 무시하고 정상 동작. → 이 단계에서 마이그레이션 실행(워크플로).
2. **Backfill(채우기)** — 배치/온라인으로 데이터 채움. 앱은 신·구 컬럼 모두 견딤.
3. **Transition(전환)** — 새 코드가 새 컬럼을 읽/쓰도록 배포. 구 경로는 아직 유지.
4. **Contract(정리)** — 신버전이 충분히 안정된 뒤, **별도 배포**에서 구 컬럼/제약 제거.

즉 "삭제·제약 강화"는 항상 **가장 마지막, 안정 확인 후, 단독 배포**로.

## 금지 (같은 배포에서 하지 말 것)

- 컬럼/테이블 rename → (add new) + (backfill) + (drop old) 세 배포로 분리.
- `DROP COLUMN` / `DROP TABLE` 를 새 코드와 **동시** 배포.
- `NOT NULL` 즉시 추가 → 먼저 nullable+기본값, backfill 후 제약 추가.
- 타입 변경 즉시 → 새 컬럼 추가 방식으로 우회.

## 파이프라인에서의 위치

- `.github/workflows/deploy-built-service.yml` 이 **gateway 경로 변경에서만**(경로 필터) deploy 이전에
  `alembic upgrade head` 를 새 이미지로 실행한다(단일 마이그레이터).
- 마이그레이션 실패 → 잡 실패 → 이미지 교체 안 함(안전 정지).
- 마이그레이션이 expand-only 라면, 이후 이미지 롤백이 안전하다.

## 불량 배포 대응 절차

1. **먼저 이미지 롤백** — `deploy.sh` 가 자동 수행(또는 수동으로 이전 태그 지정).
   스키마가 하위호환이면 이걸로 복구 완료.
2. **스키마 다운그레이드는 최후수단** — 데이터 손실 위험. 반드시:
   - 사전 백업 확인(`pg_backup.sh` 최신 스냅샷 / Supabase PITR).
   - 파괴적 다운그레이드는 점검창(maintenance) 잡고 수동 검토 후 실행.
   - `alembic downgrade <rev>` 는 "되돌릴 수 있게 작성된" 마이그레이션에만.
3. **원인 수정 후 재-전진** — 다운그레이드보다 "고쳐서 다시 upgrade"가 안전한 경우가 많다.

## 배포 전 체크리스트

```
[ ] 이번 마이그레이션은 expand-only(추가만)인가?  파괴적 변경 없음?
[ ] 구버전 코드가 이 스키마에서 그대로 동작하는가?(하위호환)
[ ] 파괴적 정리(Contract)는 별도 배포로 분리했는가?
[ ] 배포 직전 DB 백업/PITR 지점 확인했는가?
[ ] downgrade() 가 필요한 마이그레이션이면 실제로 되돌려봤는가?(스테이징)
```
