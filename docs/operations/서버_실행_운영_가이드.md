# 서버 실행·운영 가이드 (단일 레포)

이 문서는 **SkinLens monorepo 를 서버에 올려 실행하고, 파이프라인의 파트별·단계별
산출물을 확인**하는 절차를 다룬다. 피부분석·처방 엔진의 세부 로직은 아직 스텁이며,
이 빌드의 목적은 **토폴로지와 데이터 흐름을 실제로 돌려 눈으로 검증**하는 것이다.

- 서버(WSL2 Ubuntu) 자체를 처음 구축한다면 먼저: [`../server-setup/windows11_ubuntu_server_setup.md`](../server-setup/windows11_ubuntu_server_setup.md)
- 배포 자동화(CI→deploy.sh)의 개념: [`../stories/07_SkinLens_배포_이야기.md`](../stories/07_SkinLens_배포_이야기.md)

---

## 0. 이 빌드가 확인시켜 주는 것

| 확인 대상 | 방법 |
|---|---|
| **파트별** 생존 | gateway `/health`·`/health/db`, 엔진은 gateway `/debug/engines` 대리 확인 |
| **단계별** 산출물 | `GET /jobs/{id}/events` — 업로드→큐→분석→처방→완료 각 단계의 JSON 스냅샷 |
| 최종 조립 결과 | `GET /jobs/{id}` 의 `result`(analysis + prescription) |
| 격리(Case A) | 엔진은 `enginenet(internal)` 전용 — 외부 포트 없음, gateway 만 호출 |

엔진 교체 시에도 이 계약(`/score`, `/prescribe`, 이벤트 스테이지)만 지키면 파이프라인·콘솔은 그대로 쓸 수 있다.

---

## 1. 전제 조건

- Docker Engine + Docker Compose v2 (`docker compose version` 확인)
- git (또는 rsync/scp 로 레포 전송)
- 리눅스 서버(WSL2 Ubuntu 포함). GPU 는 나중 단계, 지금은 불필요.

---

## 2. 레포를 서버에 올리기

**A. git 사용(권장)**
```bash
ssh you@server
git clone <your-repo-url> skinlens && cd skinlens
```

**B. 로컬에서 rsync 전송(레포가 아직 원격에 없을 때)**
```bash
# 로컬 PC 에서
rsync -avz --exclude '.git' --exclude 'deploy/env/.env*' \
      ./skinlens/  you@server:~/skinlens/
```
> `deploy/env/.env*` 는 서버에서 직접 만든다(비밀은 전송하지 않음).

## 3. 최초 설정 (한 번)

```bash
cd ~/skinlens

# 3-1) 환경 파일
cp deploy/env/.env.example        deploy/env/.env
cp deploy/env/.env.images.example deploy/env/.env.images
#   deploy/env/.env 편집: POSTGRES_PASSWORD / DATABASE_URL 을 URL-safe 값으로.
#   (dev/staging 은 로컬 db, 운영은 DATABASE_URL 을 Supabase 로)

# 3-2) 개발자 페이지 Basic Auth 계정 (콘솔 접근용)
htpasswd -bc deploy/nginx/.htpasswd admin '강한_비밀번호'
#   htpasswd 가 없으면: sudo apt-get install -y apache2-utils

# 3-3) 로컬 접속용 호스트명(도메인 없이 브라우저로 볼 때). 서버의 /etc/hosts 또는
#      접속하는 PC 의 hosts 에 추가:
#   127.0.0.1  www.localhost api.localhost dev.localhost
```

## 4. 실행 (dev — 소스 빌드 + 로컬 db)

모든 기동 명령은 [`deploy/scripts/sl`](../../deploy/scripts/sl) 로 통일한다(Windows는 `sl.ps1`):

```bash
deploy/scripts/sl up dev     # = docker compose -f compose.base.yml -f compose.dev.yml up -d --build
deploy/scripts/sl ps dev     # 컨테이너 상태
```

> `make dev-up`, `make ps` 같은 기존 Make 타겟도 그대로 동작한다(내부에서 `sl` 호출).

`dev` 오버레이는 `DEV_DEBUG=1`(엔진 헬스 대리 확인)과 `STAGE_DELAY_SEC=1`(단계 사이 1초 지연 →
진행이 눈에 보임)을 켠다.

### 4-1. 파트별 상태 확인

API 는 `api` vhost(Host 헤더 `api.localhost`)로 들어간다. 콘솔은 `dev` vhost 의
same-origin `/api` 프록시를 쓴다.

```bash
curl -s -H 'Host: api.localhost' http://localhost/health          # gateway
curl -s -H 'Host: api.localhost' http://localhost/health/db       # db
curl -s -H 'Host: api.localhost' http://localhost/debug/engines   # 엔진(대리)
```

기대 출력:
```
{"status":"ok"}
{"db":"ok"}
{"engine-analysis":{"reachable":true,"status_code":200,"body":{"status":"ok"}},
 "engine-prescription":{"reachable":true,"status_code":200,"body":{"status":"ok"}}}
```

### 4-2. 점검 콘솔 (브라우저)

`http://dev.localhost/` 접속 → Basic Auth 로그인 → 콘솔에서
**파트 상태 · 이미지 업로드 · 단계별 타임라인**을 실시간으로 확인.
(콘솔은 `dev` vhost 뒤 same-origin `/api` 로 호출하므로 CORS 불필요.)

### 4-3. 단계별 산출물 확인 (curl)

```bash
H='-H Host:api.localhost'
JOB=$(curl -s $H -F "image=@sample.jpg;type=image/jpeg" http://localhost/analyze \
      | python3 -c "import sys,json;print(json.load(sys.stdin)['job_id'])")

curl -s $H http://localhost/jobs/$JOB/events | python3 -m json.tool   # 단계 타임라인
curl -s $H http://localhost/jobs/$JOB       | python3 -m json.tool   # 최종 result
```

로컬 검증에서 실제로 관측된 타임라인(스텁 엔진):
```
06:41:43  uploaded              {"ext":".png","bytes":73,"inputs_present":["original_filename"]}
06:41:43  queued
06:41:44  claimed               {"worker":"..."}
06:41:44  analysis:request      {"engine":"http://engine-analysis:8000","image_key":"<uid>/<job>/original.png"}
06:41:45  analysis:result       {"score":46,"metrics":{"pore":34,"redness":96,...},"engine":"analysis-stub"}
06:41:45  prescription:request  {"engine":"http://engine-prescription:8000","inputs":["analysis"]}
06:41:46  prescription:result   {"grade":"보통","score":46.0,"prescription_ratio_pct":1.0,...}
06:41:46  done                  {"ok":true}
```
최종 `result` 는 `analysis` + `prescription` 이 조립된 형태다.

### 4-4. 파트별 로그

```bash
deploy/scripts/sl logs dev           # 전체 팔로우
deploy/scripts/sl logs dev gateway   # 특정 서비스만
```

### 4-5. 정지

```bash
deploy/scripts/sl down dev           # 컨테이너 정리(볼륨 유지)
# 볼륨까지: ... compose ... down -v
```

## 5. 스테이징 / 운영으로 올리기

원리는 동일한 `compose.base.yml` 에 오버레이만 바꾸는 것이다.

| 환경 | 명령 | DB | 이미지 |
|---|---|---|---|
| staging(WSL) | `sl up staging` | 로컬 postgres | `.env.images` 태그 |
| prod(VPS) | `sl up prod` (기동 전 `sl doctor prod` 자동 검사) | Supabase(`DATABASE_URL`) | `.env.images` 태그 + TLS |

환경별 절차 전체는 [`환경별_빌드_기동_절차.md`](환경별_빌드_기동_절차.md) 참조.

CI(`.github/workflows/`)가 변경 서비스만 빌드해 서버의 `deploy/scripts/deploy.sh` 를 호출한다.
수동 배포는 `sl deploy`가 같은 스크립트를 감싼다:
```bash
# 스테이징에서 gateway 를 새 이미지로 (헬스 게이트 + 실패 시 자동 롤백)
deploy/scripts/sl deploy gateway sl_gateway:$(git rev-parse --short HEAD) --env staging

# 운영에서 엔진을 GHCR 이미지로
deploy/scripts/sl deploy engine-analysis \
  ghcr.io/coteleafdev/skinlens-engine-analysis:sha --env production --pull
```

> 운영에서는 `compose.prod.yml` 에 로컬 db 가 없으므로 `deploy/env/.env` 의
> `DATABASE_URL` 이 반드시 Supabase 를 가리켜야 한다.

## 7. 트러블슈팅

| 증상 | 확인 |
|---|---|
| gateway `unhealthy` | `logs gateway` → DB 접속(`DATABASE_URL`) 실패가 대부분. `/health/db` 확인 |
| 업로드 415/413 | 형식(jpeg/png/webp)·크기(25MB). nginx `client_max_body_size` 와 `MAX_UPLOAD_BYTES` 정렬 |
| job 이 `queued` 에서 안 넘어감 | worker 로그 확인(`logs worker`). db 접속/엔진 헬스 |
| `analysis:skipped` | 저장된 이미지 경로 없음 — Storage 볼륨/키 규약 확인 |
| `/debug/engines` 404 | `DEV_DEBUG` 가 꺼짐(운영 정상). dev 에서만 켠다 |
| 콘솔에서 401 | dev vhost Basic Auth — `deploy/nginx/.htpasswd` 계정 |
| engine 이 외부에서 안 열림 | 정상. 엔진은 `enginenet(internal)` 폐쇄망(Case A) |

## 8. 자동화 테스트 실행 가이드

SkinLens 프로젝트는 기능 및 보안성 검증을 위해 `pytest` 기반의 자동화 테스트 스위트를 [`tests/`](../../tests/) 폴더에 보관하고 있습니다.

### 8-1. 테스트 구조
*   **단위 테스트 (`pytest -m "not integration"`)**: DB나 네트워크 호출 없이 FastAPI/Pydantic 규격, 이미지 바이너리 매직 바이트 필터, 규칙 엔진 로직 등을 독립 실행하여 검증합니다.
*   **통합 테스트 (`pytest -m integration`)**: 실제/임시 PostgreSQL 데이터베이스와 연동하여 비동기 Job 생성, DB 트랜잭션, 락킹, 소유권 권한 RLS, API Gateway ➔ Worker ➔ 엔진 파이프라인 E2E 흐름을 검증합니다.

### 8-2. 테스트 실행 명령
루트의 [`Makefile`](../../Makefile) 단축 명령을 활용합니다.

```bash
# 1) 단위 테스트 실행 (데이터베이스 불필요)
make test

# 2) 통합 테스트 실행 (DATABASE_URL 설정 및 DB 가동 필요)
make itest

# 3) 엔드투엔드 스모크 테스트 (컨테이너 스택 기동 후 로컬 업로드/폴링 흐름 전체 검증)
make smoke
```
