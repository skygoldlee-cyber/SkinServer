## P0 #2 — Rate limit 실제 클라이언트 IP 인식

**파일:** `deploy/nginx/conf.d/00-hardening.conf`

**문제:** 운영에서 nginx 앞엔 Caddy(`compose.tls.yml`)가 있고, 실제 클라이언트 IP는 `X-Forwarded-For`에 있다. nginx가 이를 복원하지 않으면 모든 요청의 `$remote_addr`가 Caddy IP로 기록돼 `limit_req_zone`이 프록시 단일 IP 기준으로 묶여 rate limit이 물리화된다.

**변경:**
```nginx
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
set_real_ip_from 192.168.0.0/16;
set_real_ip_from 100.64.0.0/10;      # CGNAT(도커 사설망 포함)
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```
- 신뢰 대역을 RFC1918 + CGNAT 도커 사설망으로 한정 → 공인 IP 스푸핑 차단.
- `real_ip_recursive on`: XFF 체인에서 마지막 비신뢰 주소를 실제 IP로 채택.
- Caddy가 본래 넣는 헤더(`deploy/caddy/Caddyfile: header_up X-Forwarded-For {remote_host}`)와 정합.
- **다운타임 없음** — `docker compose exec nginx nginx -s reload` 만으로 반영.

## P1 #4 — DB 비밀번호 필수값화

**파일:** `deploy/compose/compose.base.yml` (gateway/worker 2곳), `deploy/env/.env.example`

**문제:** `DATABASE_URL` fallback이 `POSTGRES_PASSWORD:-app_pw`를 기본값으로 사용 → `.env` 누락 시 약한 비밀번호로 기동 가능.

**변경:**
```yaml
# before
DATABASE_URL: ${DATABASE_URL:-postgresql://...:${POSTGRES_PASSWORD:-app_pw}@db:5432/...}
# after
DATABASE_URL: ${DATABASE_URL:-postgresql://...:${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in deploy/env/.env}@db:5432/...}
```
- `:?` 필수값 연산자로, `.env`가 없으면 compose가 즉시 오류(fail-fast).
- `deploy/env/.env.example`에 필수값 안내 주석 추가.
- ⚠️ **주의:** 기존 `.env`에 `POSTGRES_PASSWORD`가 없으면 다음 `up`부터 실패한다. 배포 전 `.env` 확인 필요.

## P1 #5 — Engine config 프로덕션 가드

**파일:** `services/engine-prescription/app/rules.py`, `deploy/compose/compose.prod.yml`

**문제:** `load_config()`가 `mixes.json`이 없으면 `mixes.example.json`으로 조용히 fallback → 운영에 예시 믹스가 배포될 위험.

**변경:**
```python
env = os.environ.get("ENV", "dev").lower()
for name in ("mixes.json", "mixes.example.json"):
    ...
    if env == "prod" and name == "mixes.example.json":
        raise RuntimeError("ENV=prod 에서는 mixes.example.json 사용 금지 ...")
```
- `compose.prod.yml`의 `worker`/`engine-analysis`/`engine-prescription`에 `ENV: prod` 배선.
- dev/staging은 example 허용(개발 편의 유지), prod만 fail-fast.

## P1 #3 — staging TLS (Caddy, ACME staging CA)

**신규 파일:** `deploy/compose/compose.staging-tls.yml`, `deploy/caddy/Caddyfile.staging`

**문제:** staging은 HTTP(80) 직결이라 devpage Basic Auth 자격증명이 평문 전송.

**변경:** Let's Encrypt **staging CA**를 쓰는 opt-in Caddy 오버레이 추가.
- `Caddyfile.staging`의 `acme_ca https://acme-staging-v02.api.letsencrypt.org/directory` → 발급 한도 소모 없이 TLS 경로 검증(브라우저 경고는 정상).
- `compose.staging-tls.yml`이 `nginx` host 포트를 `!reset`으로 비우고 Caddy가 80/443 소유.

**사용법:**
```bash
docker compose -f deploy/compose/compose.base.yml \
               -f deploy/compose/compose.staging.yml \
               -f deploy/compose/compose.staging-tls.yml \
               --env-file deploy/env/.env --env-file deploy/env/.env.images up -d
```
- **전제:** staging 도메인 DNS가 해당 박스를 가리켜야 ACME 통과. `Caddyfile.staging`의 도메인/이메일을 실제 값으로 교체.
- 순수 로컬 WSL 개발(도메인 없음)은 기존 HTTP 직결 유지(기본값, 위험 낮음).

## P3 #10 — useJob 지수 백오프

**파일:** `apps/webapp/src/hooks/useJob.ts`

**문제:** 고정 1.5s 폴리은 모바일/저전력 환경에서 배터리·데이터 소모.

**변경:**
- 상태 변화(=진전) 시 `intervalMs`(기본 1500ms)로 리셋, 물변화 시 `maxIntervalMs`(기본 15000ms)까지 **지수 백오프**(`delay * 2`).
- `document.visibilityState === "hidden"`이면 해당 틱 유예(백그라운드 배터리 절약).
- 오류 시에도 백오프해 실패 루프가 서버를 두드리지 않게 함.
- `done`/`error` 종료·cleanup 로직은 기존과 동일. 시그니처: `useJob(jobId, intervalMs=1500, maxIntervalMs=15000)`(후방 호환).

## P3 #9 — 스키마 diff 테스트

**신규 파일:** `tests/common/test_schema_drift.py`

**문제:** gateway auto-DDL(dev, `main.py`의 `DDL`)과 운영 마이그레이션(`deploy/db/migrations/0001_init.sql`)이 같은 DDL을 이중 정의 → 한쪽만 바뀌면 dev/prod 스키마 drift.

**변경:** 정규화(주석·공백·콤마·괄호 정리) 후 CREATE 문을 세미콜론 단위로 나눠 **집합 비교**.
- 표면적 차이(인덱스 컬럼 정렬용 스페이스 등)는 무시하고 의미만 비교.
- drift 발생 시 `unit` 잡(`.github/workflows/tests.yml`)에서 즉시 실패.
- CI 추가 작업 불필요 — 기존 `pytest -m "not integration"` 범위에 자동 포함.

## 검증 상태

이 변경은 **정적 대조 검증**까지 완료했고, 실행 검증은 별도 환경이 필요하다.

- 로컬 터미널에 실행 가능한 Python/Node/Docker 런타임이 없어(Microsoft Store 스텁만 존재) `pytest`/`tsc`를 이 환경에서 실행하지 못했다.
- 각 변경은 소비자와 정적 대조로 일치 확인: nginx↔Caddy XFF 헤더, compose `:?` 문법, `rules.py` 분기, DDL↔migration 정합, useJob 상태 머신.
- **실행 검증 방법:**
  - 단위 테스트: `pip install -r requirements-dev.txt && python3 -m pytest -m "not integration"` (또는 CI `unit` 잡)
  - nginx 문법: `docker compose exec nginx nginx -t`
  - compose 문법: `docker compose -f ... config --quiet`
  - 프론트엔드: `cd apps/webapp && npm ci && npm run build`(또는 `tsc --noEmit`)

1. **`.env` 확인(#4):** `POSTGRES_PASSWORD` 미설정 시 다음 기동부터 실패 → 배포 전 `deploy/env/.env`에 값 존재 여부 확인.
