# 환경별 빌드·기동 절차 가이드

이 문서는 SkinLens 모노레포를 **개발(dev) / 스테이징(staging) / 운영(prod)** 환경에서
각각 빌드하고 기동하는 절차를 정리한 것이다.

> **모든 기동 명령의 진실원본은 [`deploy/scripts/sl`](../../deploy/scripts/sl) 이다.**
> 이 문서의 명령은 전부 `sl` 사용법이며, 긴 compose one-liner는 부록에서만 참조한다.
> Windows 네이티브에서는 [`deploy/scripts/sl.ps1`](../../deploy/scripts/sl.ps1)을 같은 인터페이스로 사용한다.

## 빠른 시작

```bash
# 최초 1회 — env 파일 생성 → 값 입력 안내 → 자가진단까지
deploy/scripts/sl init dev

# 기동
deploy/scripts/sl up dev        # 소스 빌드 포함
deploy/scripts/sl up staging    # .env.images 태그 이미지
deploy/scripts/sl up prod       # TLS 오버레이 포함, doctor 자동 통과해야 기동

# 상태·로그·정지 (env 생략하면 실행 중 컨테이너로 추론)
deploy/scripts/sl ps dev
deploy/scripts/sl logs dev gateway
deploy/scripts/sl down dev

# 기동 전 자가진단
deploy/scripts/sl doctor prod
```

`make` 습관이 있다면 그대로 써도 된다 — [`Makefile`](../../Makefile)은 `sl`을 호출하는
얇은 래퍼다 (`make dev-up`, `make staging-up`, `make prod-up`, `make doctor ENV=prod` …).

## 0. 환경 비교 요약

| 구분 | dev | staging | prod |
|---|---|---|---|
| 오버레이 | [`compose.dev.yml`](../../deploy/compose/compose.dev.yml) | [`compose.staging.yml`](../../deploy/compose/compose.staging.yml) | [`compose.prod.yml`](../../deploy/compose/compose.prod.yml) + [`compose.tls.yml`](../../deploy/compose/compose.tls.yml) |
| **빌드 방식** | 서버에서 소스 직접 빌드 (`sl up dev` 가 `--build`) | 빌드 없음 — `.env.images` 태그 이미지 | 빌드 없음 — 레지스트리 이미지 pull (`pull_policy: always`) |
| **기동 명령** | `sl up dev` | `sl up staging` | `sl up prod` |
| **env 파일** | `deploy/env/.env` | `.env` + `.env.images` | `.env` + `.env.images` |
| **DB** | Supabase (`DATABASE_URL`) | Supabase | Supabase (로컬 db 없음) |
| **인증** | `AUTH_MODE=dev` (X-User-Id 허용) | `AUTH_MODE=strict` (JWT 필수) | `AUTH_MODE=strict` + `ENV=prod` fail-fast |
| **디버그** | `DEV_DEBUG=1` (`/debug/engines` 노출) | off | off |
| **단계 지연** | `STAGE_DELAY_SEC=1` | 없음 | 없음 |
| **TLS** | 없음 (로컬 `*.localhost`) | 없음 | Caddy 자동 HTTPS |
| **배포 주체** | 개발자 수동 | CI → `deploy.sh` | CI → `deploy.sh` |

## 1. 공통 전제 조건

`sl init <env>`가 아래를 자동으로 처리한다. 수동으로 하려면:

1. **Docker Engine + Compose v2** — `sl doctor <env>` 가 검사해 준다.
2. **레포 체크아웃**
3. **환경 파일 (최초 1회)** — `sl init <env>` 가 예시를 복사하고,
   템플릿 값(`CHANGE_ME`, `<...>`)이 남아 있으면 대화형으로 입력을 받는다.
   - `DATABASE_URL` — Supabase postgres 접속 문자열 (**필수**, 없으면 compose가 fail-fast)
   - `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` — Storage/Auth
   - 운영 strict 인증 시 `SUPABASE_JWT_SECRET` (또는 `JWT_SECRET`)
4. **개발자 콘솔 Basic Auth (dev)** — `sl init dev` 가 물어보고 생성.
5. **로컬 호스트명 (dev 브라우저 접속)** — `sl init dev` 가 OS별 등록법을 안내.

## 2. dev — 소스 빌드 + 로컬 실행

### 2-1. 빌드 & 기동

```bash
sl up dev          # compose base+dev up -d --build
```

코드만 고쳤을 때: 다시 `sl up dev` (또는 `make dev-build` 후 `sl up dev`).

### 2-2. 확인

```bash
sl ps dev
sl logs dev                                               # 전체
sl logs dev gateway                                       # 특정 서비스만

curl -s -H 'Host: api.localhost' http://localhost/health          # gateway
curl -s -H 'Host: api.localhost' http://localhost/health/db       # DB
curl -s -H 'Host: api.localhost' http://localhost/debug/engines   # 엔진 대리 확인 (dev 전용)
```

### 2-3. 호출 방법

- **인증**: `AUTH_MODE=dev` — JWT 없이 `X-User-Id: <uuid>` 헤더로 테스트 가능
- **점검 콘솔**: `http://dev.localhost/` → Basic Auth 로그인
- **스모크 테스트**: `make smoke` (업로드 → Job 완료까지)

### 2-4. 정지

```bash
sl down dev
```

---

## 3. staging — 배포 이미지 기동

서버에서는 빌드하지 않는다. 이미지는 CI(`.github/workflows/`)가 빌드해 태그를 만들고,
태그는 `deploy/env/.env.images`에 기록된다.

### 3-1. 기동

```bash
sl up staging
```

### 3-2. 개별 서비스만 교체 (배포 스크립트)

[`deploy/scripts/deploy.sh`](../../deploy/scripts/deploy.sh)를 `sl`이 감싼다 —
헬스체크 게이트와 실패 시 자동 롤백 포함:

```bash
sl deploy gateway sl_gateway:$(git rev-parse --short HEAD) --env staging
```

동작 순서: `.env.images` 태그 원자적 교체(flock 직렬화) → `up -d` → 헬스 대기(기본 120s)
→ 실패 시 이전 태그로 자동 롤백.

### 3-3. 호출 방법

- **인증**: `AUTH_MODE=strict` — Supabase JWT 필요 (`Authorization: Bearer <JWT>`)
- `/debug/engines` 는 노출되지 않는다.

### 3-4. 정지

```bash
sl down staging
```

## 4. prod — 운영 기동 (TLS + fail-fast)

### 4-1. 사전 확인

`sl up prod`는 기동 전 **자동으로 `sl doctor prod`를 실행**하고, 실패 항목이 있으면
기동하지 않는다. doctor가 검사하는 것:

- `deploy/env/.env`의 `DATABASE_URL`이 실제 Supabase 주소인가 (prod엔 로컬 db 없음)
- JWT 시크릿이 있는가 (strict 필수)
- `.env.images`가 있는가
- GHCR 로그인 상태 (비공개 이미지 pull 시)
- docker / compose v2

이 외 운영 전제: 도메인 DNS가 서버를 가리킬 것(Caddy 인증서 자동 발급),
Supabase RLS/Storage 정책 적용([`deploy/supabase/policies/0001_rls_and_storage.sql`](../../deploy/supabase/policies/0001_rls_and_storage.sql)).

### 4-2. 기동

```bash
sl up prod       # doctor 자동 통과 후 compose base+prod+tls up -d
```

### 4-3. fail-fast 가드 (기동 시점에 설정 오류 차단)

`ENV=prod`일 때 다음이 아니면 **기동 자체가 거부**된다:

- `AUTH_MODE != strict` → gateway 부팅 거부
- 처방 엔진이 example config fallback → 부팅 거부 ([`rules.py`](../../services/engine-prescription/app/rules.py))
- `DATABASE_URL` 미설정 → compose 즉시 오류 (`:?` 문법)

### 4-4. 이미지 교체

```bash
sl deploy engine-analysis ghcr.io/coteleafdev/skinlens-engine-analysis:<sha> --env production --pull
```

### 4-5. 호출 방법

- HTTPS 도메인: `https://api.example.com/health`
- 모든 API에 `Authorization: Bearer <SUPABASE_JWT>` 필수 (없으면 401)

### 4-6. 정지

```bash
sl down prod     # 확인 프롬프트 있음 (실수 방지)
```

`sl`이 자동으로 `-f`로 얹는다 (deploy.sh와 동일 규칙). 별도 인자 불필요.

## 6. 기동 후 검증 공통 절차

1. **파트별 헬스** — gateway `GET /health`, `/health/db`; 엔진은 dev에선 `/debug/engines`,
   staging/prod에선 `sl ps <env>`의 health 상태
2. **E2E 스모크** — `make smoke`
3. **단계별 산출물** — `GET /jobs/<job_id>/events` (타임라인), `GET /jobs/<job_id>` (최종 result)

## 7. 트러블슈팅 요약

| 증상 | 원인/확인 |
|---|---|
| `sl up` 전에 막힘 | `sl doctor <env>` 출력의 "고치는 법"부터 처리 |
| gateway `unhealthy` | `DATABASE_URL` 오류가 대부분. `/health/db` 확인 |
| staging/prod에서 401 | JWT 누락 또는 만료 — `AUTH_MODE=strict` 정상 동작 |
| `/debug/engines` 404 | `DEV_DEBUG` 꺼짐 (staging/prod 정상) |
| job이 `queued`에서 멈춤 | `sl logs <env> worker` — DB 접속 또는 엔진 헬스 |
| prod 기동 즉시 실패 | fail-fast 가드: `AUTH_MODE`, 엔진 config, `DATABASE_URL` 확인 |
| 엔진이 외부에서 안 열림 | **정상** — 엔진은 `enginenet(internal)` 폐쇄망(Case A) |
| 콘솔 401 | dev vhost Basic Auth — `deploy/nginx/.htpasswd` 계정 확인 |

상세는 [`서버_실행_운영_가이드.md`](서버_실행_운영_가이드.md) §7 및
[`파이프라인_체크포인트_트러블슈팅.md`](파이프라인_체크포인트_트러블슈팅.md) 참조.

## 부록 A. 남부 compose one-liner (참고용 — `sl`이 감추는 실제 명령)

```bash
# dev
docker compose -f deploy/compose/compose.base.yml -f deploy/compose/compose.dev.yml \
  --env-file deploy/env/.env up -d --build

# staging
docker compose -f deploy/compose/compose.base.yml -f deploy/compose/compose.staging.yml \
  --env-file deploy/env/.env --env-file deploy/env/.env.images up -d

# prod
docker compose -f deploy/compose/compose.base.yml -f deploy/compose/compose.prod.yml \
  -f deploy/compose/compose.tls.yml \
  --env-file deploy/env/.env --env-file deploy/env/.env.images up -d
```
