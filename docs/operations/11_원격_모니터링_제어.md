# Windows → Linux 서버 원격 모니터링·제어

> 서버가 리눅스(외부 호스팅·VPS·또는 다른 방의 리눅스 박스)에서 돌 때,
> **외부 Windows PC에서 서버 상태를 보고(모니터링)·원격으로 조작(제어)** 하는 표준 방법입니다.

- 대상 독자: 운영자 (Windows PC 사용)
- 전제: 서버에 이 리포가 체크아웃돼 있고, SSH 키 접속이 이미 설정돼 있음
  ([windows11_ubuntu_server_setup.md](../server-setup/windows11_ubuntu_server_setup.md) 5~6장)
- 도구: `deploy/scripts/remote.ps1` (또는 `remote.cmd`) + 서버측 `deploy/ops/remote-status.sh`

---

## 1. 한눈에 보기

```
[외부 Windows PC]                      [리눅스 서버]
 remote.ps1 ──SSH(22)──▶  sshd ──▶  bash deploy/ops/remote-status.sh   (상태 수집)
                                   bash deploy/scripts/sl …           (기동/정지/로그/ps)
                                   bash deploy/scripts/deploy.sh …    (배포·자동롤백)
```

- **모니터링**은 SSH 한 번으로 서버측 에이전트(`remote-status.sh`)가
  컨테이너·헬스·디스크·메모리·큐·GPU·최근 오류를 한꺼번에 긁어 돌려준다.
- **제어**는 기존 서버측 CLI(`sl`, `deploy.sh`)를 SSH 경유로 그대로 호출한다.
  서버에 새로 설치하는 에이전트·데몬·포트 개방이 **없다**(SSH만 있으면 됨).

| 파일 | 역할 | 실행 위치 |
|---|---|---|
| [`deploy/scripts/remote.ps1`](../../deploy/scripts/remote.ps1) | 통합 원격 CLI (PowerShell) | Windows |
| [`deploy/scripts/remote.cmd`](../../deploy/scripts/remote.cmd) | cmd.exe 래퍼 (실행정책 불필요) | Windows |
| [`deploy/ops/remote-status.sh`](../../deploy/ops/remote-status.sh) | 상태 스냅샷 에이전트 | 리눅스 서버 |
| [`deploy/env/remote.env.example`](../../deploy/env/remote.env.example) | 접속 설정 템플릿 | Windows |

## 2. 최초 1회 설정

### 2-1. SSH 키 접속 확인

원격 제어의 전제는 **비밀번호 없이 키로** 들어가는 것입니다.

```powershell
# Windows 에서 서버로 키 접속이 되는지 먼저 확인
PS> ssh ubuntu@your.server.example.com "echo ok; hostname"
```

아직이면 서버 설정 문서 5~6장(SSH 서버·키 등록)을 먼저 완료하세요.
로컬 `~/.ssh/config` 에 별칭을 두면 이후 명령이 짧아집니다:

```text
Host myserver
    HostName your.server.example.com
    User ubuntu
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

### 2-2. 접속 설정 파일 작성

```powershell
PS> copy deploy\env\remote.env.example deploy\env\remote.env
PS> notepad deploy\env\remote.env
```

```ini
RemoteTarget=myserver          # 또는 ubuntu@your.server.example.com
RemoteDir=~/SkinServer         # 서버에서 이 리포가 체크아웃된 위치
# SshPort=22
# IdentityFile=C:\Users\you\.ssh\id_ed25519
```

> ⚠ `remote.env` 는 `.gitignore` 에 등록돼 있어 커밋되지 않습니다.

### 2-3. 연결 테스트

```powershell
PS> .\deploy\scripts\remote.cmd test-ssh
✓ SSH 연결 정상
```

## 3. 모니터링 (읽기)

서버를 **바꾸지 않고** 상태만 봅니다.

```powershell
# 전체 상태 스냅샷 (권장 진입점) — 컨테이너/헬스/디스크/메모리/큐/GPU/최근오류
PS> .\deploy\scripts\remote.cmd status

# 5초마다 자동 갱신 대시보드 (Ctrl+C 종료)
PS> .\deploy\scripts\remote.cmd status -Watch

# 컨테이너 목록만
PS> .\deploy\scripts\remote.cmd ps

# 로그 팔로우 (생략 시 전체, 서비스 지정 가능)
PS> .\deploy\scripts\remote.cmd logs gateway

# 엔드포인트 헬스만 빠르게 (종료코드로 정상/이상 판별 → 스크립팅용)
PS> .\deploy\scripts\remote.cmd health

# 원격 자가진단 (기동 가능 상태인지)
PS> .\deploy\scripts\remote.cmd doctor prod
```

`status` 출력 예:

```
== 호스트 (ip-10-0-1-5) · env=prod ==
  [ OK ] 디스크 41%
  [ OK ] 메모리 58% 사용
  [ OK ] GPU VRAM 22% (3612/16380MiB)
== 컨테이너 ==
  [ OK ] gateway (sl_gateway) — running Up 3 hours (healthy)
  [ OK ] worker (sl_worker) — running Up 3 hours
== 엔드포인트 ==
  [ OK ] gateway /health (container) HTTP 200
== 큐 적체 (DB) ==
  [ OK ] 큐 대기 2건
== 최근 오류 (gateway · worker) ==
  (최근 오류 없음)

정상: OK 7
```

> 종료코드: 정상 `0` · FAIL 있으면 `1`. `health`/`status` 를 작업 스케줄러나
> 감시 스크립트에 걸어 **이상 시에만 알림**을 볼 수 있습니다(§6).

## 4. 제어 (쓰기)

서버 상태를 **바꿉니다.** prod 대상 동사는 실수 방지로 확인 프롬프트를 띄웁니다
(자동화 시 `-Yes` 로 생략).

```powershell
# 스택 기동 / 정지
PS> .\deploy\scripts\remote.cmd up prod
PS> .\deploy\scripts\remote.cmd down prod

# 개별 서비스 재시작
PS> .\deploy\scripts\remote.cmd restart worker prod

# 개별 서비스 배포 (새 이미지로 교체 → 헬스 대기 → 실패 시 자동 롤백)
PS> .\deploy\scripts\remote.cmd deploy gateway ghcr.io/me/sl_gateway:abc123 -Env prod -Pull
```

배포는 서버측 `deploy.sh` 가 그대로 실행되므로, **`.env.images` 원자적 교체 →
헬스체크 → 실패 시 이전 태그 자동 롤백** 로직이 동일하게 적용됩니다.

## 5. 관리 포트 터널링 (DB·콘솔)

외부에 열지 않은 관리 포트(DB 5432·adminer 8080·uptime-kuma 3001 등)는
**SSH 로컬 포워딩**으로만 접근합니다(서버 하드닝 정책과 일치).

```powershell
# 로컬 8080 → 서버 8080 (adminer 등). Ctrl+C 로 종료.
PS> .\deploy\scripts\remote.cmd tunnel 8080
# 브라우저에서 http://localhost:8080 접속

# 로컬 5433 → 서버 5432 (DB 클라이언트 연결용)
PS> .\deploy\scripts\remote.cmd tunnel 5433 5432
```

## 6. 자동 감시 (선택)

이상이 생기면 알려주는 감시는 두 겹으로 둘 수 있습니다.

1. **서버 자체 감시** — 서버의 cron 이 [`deploy/ops-jobs/observability/alert.sh`](../../deploy/ops-jobs/observability/alert.sh) 를
   주기 실행해 웹훅(Slack/Discord)으로 통지. 서버가 살아있는 한 Windows 가 꺼져 있어도 동작.
2. **Windows 측 감시** — Windows 작업 스케줄러가 `remote.cmd health` 를 주기 실행하고,
   종료코드 `1` 이면 알림. 서버는 살았지만 외부 경로(엣지)만 죽은 경우를 잡는 데 유용.

```powershell
# 작업 스케줄러 등록 예 (5분마다 헬스 확인, 실패 시에만 이벤트 로그)
PS> schtasks /create /tn "SkinLens-RemoteHealth" /sc minute /mo 5 `
    /tr "powershell -NoProfile -ExecutionPolicy Bypass -File C:\Project\SkinServer\deploy\scripts\remote.ps1 health"
```

## 7. 임의 명령 실행

등록된 동사 외 한 줄짜리 명령은 `exec` 로 실행합니다.

```powershell
PS> .\deploy\scripts\remote.cmd exec "docker stats --no-stream"
PS> .\deploy\scripts\remote.cmd exec "df -h /"
PS> .\deploy\scripts\remote.cmd exec "uptime"
```

## 8. 트러블슈팅

| 증상 | 원인·조치 |
|---|---|
| `접속 대상이 없습니다` | `remote.env` 미작성 → §2-2. 또는 `-Target user@host` 인자 사용 |
| `SSH 연결 실패` | 키 미등록/호스트 오타 → `ssh user@host` 단독으로 먼저 확인(§2-1) |
| `bash: .../sl: No such file` | 서버의 `RemoteDir` 이 다름 → `remote.env` 의 `RemoteDir` 를 실제 체크아웃 경로로 |
| `status` 에서 `docker 데몬 무응답` | 서버 docker 다운 → `up` 전에 서버 접속해 `systemctl status docker` 확인 |
| 상태는 정상인데 외부 접속만 안 됨 | 엣지(Caddy/방화벽) 문제 → `remote.env` 에 `GATEWAY_HEALTH_URL` 설정해 엣지 경로까지 감시 |
| prod 동사가 매번 물어봄 | 의도된 안전장치. 스크립팅 시에만 `-Yes` 사용 |

---

## 9. 보안 노트

- 원격 제어는 **SSH 키 인증**에만 의존한다. 비밀번호 로그인은 서버 `sshd_config` 에서
  `PasswordAuthentication no` 로 닫혀 있어야 한다(설정 문서 6-4).
- 서버에 **추가 포트를 열지 않는다.** 모든 운영 트래픽은 22번(SSH) 하나로만 들어간다.
- `remote.env` 에는 호스트·키 경로만 두고, **비밀번호·토큰은 절대 넣지 않는다.**
- prod 제어 동사는 확인 프롬프트가 기본이며, `-Yes` 는 신뢰된 자동화에서만 사용한다.
