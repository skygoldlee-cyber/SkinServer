# 파이프라인 체크포인트 · 트러블슈팅 가이드

앱 요청부터 최종 결과까지 **각 홉(hop)의 체크포인트**(무엇이 정상인지 + 확인 방법)와,
증상→원인→조치를 정리한다. 실행/운영 절차는 [`서버_실행_운영_가이드.md`](./서버_실행_운영_가이드.md),
엔진 교체 지점은 [`../architecture/엔진_baseline_교체_가이드.md`](../architecture/엔진_baseline_교체_가이드.md) 참조.

전체 흐름:
```
Flutter 앱 ──①──> nginx(엣지) ──②──> gateway ──③──> Postgres(job 등록)
                                                   │
worker ──④(claim)──> ⑤ analysis 엔진 ──> ⑥ prescription 엔진 ──> ⑦ 결과 기록
앱 ──⑧(폴링)──> gateway ──> job/status/events
```
각 단계는 `job_events` 에 남으므로, 막힌 지점은 대개 **마지막으로 찍힌 stage** 로 특정된다.

---

## 체크포인트 (단계별 '정상' 신호)

| # | 홉 | 정상 신호 | 확인 방법 |
|---|---|---|---|
| ① | 앱→엣지 | 요청이 엣지에 도달(80/443) | `curl -I -H 'Host: api.localhost' http://<서버>/health` → 200 |
| ② | 엣지→gateway | api vhost 가 gateway 로 프록시 | `/health` 200, nginx access log 에 upstream 200 |
| ③ | gateway→DB | job insert + `uploaded`,`queued` 이벤트 | `GET /jobs/{id}/events` 첫 두 줄 |
| ④ | worker claim | `queued`→`processing`, `claimed` 이벤트 | events 에 `claimed`, worker 로그 "처리 시작" |
| ⑤ | analysis | `analysis:request`→`analysis:result`(10지표) | events 의 `analysis:result` detail |
| ⑥ | prescription | `prescription:request`→`prescription:result` | events 의 `prescription:result`(per_metric·mixes) |
| ⑦ | 결과 기록 | `done`, `result` 채워짐 | `GET /jobs/{id}` status=done, result≠null |
| ⑧ | 앱 폴링 | status 전이 관측 | 앱이 done/error 수신 |

> **빠른 진단 원칙**: `GET /jobs/{id}/events` 의 **마지막 stage** 를 본다.
> `claimed` 에서 멈춤 → 엔진/worker 문제(⑤⑥). `analysis:request` 에서 멈춤 → 분석 엔진.
> 이벤트가 `queued` 뿐 → worker 미기동(④). 이벤트가 없음 → gateway/DB(③).

---

## 상태 전이 판독표

| 마지막 stage | 해석 | 우선 확인 |
|---|---|---|
| (이벤트 없음) | job 미등록 | gateway 로그, `/health/db` |
| `queued` | worker 가 안 집어감 | worker 컨테이너 up? DB 접속? |
| `claimed` / `analysis:request` | 분석 엔진 호출 실패/지연 | `logs engine-analysis`, enginenet 연결 |
| `analysis:result` 후 정지 | 처방 입력 없음/처방 엔진 오류 | 입력(분석·설문·PCR) 유무, `logs engine-prescription` |
| `error` | 처리 중 예외(또는 데드레터) | `GET /jobs/{id}` 의 `error` 문자열, `attempts` |
| `reaped` | 멈춘 processing 회수됨 | worker 재기동/엔진 지연 여부. `attempts` 확인 |
| `prescribed` | 처방 기록됨(→ 곧 done) | 정상 진행 |
| `done` | 정상 | — |

## 트러블슈팅 (증상 → 원인 → 조치)

### A. 업로드/엣지 (①②③)
| 증상 | 원인 | 조치 |
|---|---|---|
| 413 | 이미지>25MB, nginx/앱 상한 | 리사이즈; `client_max_body_size` 와 `MAX_UPLOAD_BYTES` 정렬 |
| 415 | 형식·매직바이트 불일치 | jpeg/png/webp 로 전송, 실제 바이트 확인 |
| 400 (survey) | survey/pcr 가 JSON object 아님 | 앱에서 `jsonEncode(map)` 확인(배열/문자열 X) |
| 502/504 | gateway 다운/지연 | `logs gateway`, `/health`; 타임아웃은 api.conf `proxy_read_timeout` |
| 이벤트 자체가 없음 | DB 미접속 | `/health/db`, `DATABASE_URL`, db 컨테이너 상태 |

### B. 워커/큐 (④)
| 증상 | 원인 | 조치 |
|---|---|---|
| `queued` 에서 정체 | worker 미기동 | `docker compose ... ps`, `logs worker` |
| worker 로그 "DB 접근 실패" | DB 다운/자격 | `/health/db`, `.env` DATABASE_URL |
| worker `unhealthy` | 하트비트(/tmp/worker_alive) 없음 | 프로세스 살아있는지, tmpfs 마운트 |
| 여러 worker 중복 처리 | 잠금 미동작 | `FOR UPDATE SKIP LOCKED` 유지 확인(코드 변경 시) |
| job 이 계속 `error` 로 감(반복) | 엔진 지속 실패 → `MAX_ATTEMPTS` 소진 데드레터 | 엔진 로그, `attempts`. 원인 해소 후 재업로드 |
| 401 (업로드) | `AUTH_MODE=strict` 인데 X-User-Id 없음 | 상류 인증 계층이 검증·주입하는지 확인(운영) |

### C. 분석 엔진 (⑤)
| 증상 | 원인 | 조치 |
|---|---|---|
| `analysis:request` 에서 멈춤 | 엔진 다운/네트워크 | `logs engine-analysis`, `/debug/engines`(dev) |
| 400 "이미지 디코드 실패" | 손상/미지원 이미지 | 원본 재확인; webp 매직바이트 |
| 매우 느림 | 모델/복원 무거움, CPU 한계 | `compose.gpu.yml`, `mem_limit/cpus` 상향 |
| 점수가 늘 극단값 | 정규화 경계 미교정 | `metrics.py` `_norm(...)` 상수 튜닝(실촬영 기준) |
| `analysis:skipped` | 저장 이미지 경로 없음 | Storage 볼륨/키 규약(`{user}/{job}/`) |

### D. 처방 엔진 (⑥)
| 증상 | 원인 | 조치 |
|---|---|---|
| "처방 입력 없음" 오류 | 분석·설문·PCR 모두 없음 | 최소 1종 전송(설문만도 가능) |
| 민감성/복합성이 placeholder | 설문 미전송 | 앱에서 survey 포함; `source:survey` 확인 |
| selected_mixes 비어있음 | trigger 등급 미달 or config 매핑 없음 | `mixes.json` `metric_to_mixes`/`trigger_grades` |
| 믹스 코드가 예시값 | 실제 배합 config 미주입 | `mixes.example.json`→`mixes.json` 로 실제 값 |
| 종합 등급과 지표별이 상충 | 종합 vs 지표별 정책 미확정 | 처방 산출 규칙 결정(아래 결정 포인트) |

### E. 결과/폴링 (⑦⑧)
| 증상 | 원인 | 조치 |
|---|---|---|
| status=error | 처리 중 예외 | `GET /jobs/{id}` 의 `error`, 해당 엔진 로그 |
| result=null 인데 done | 결과 기록 실패 | worker `finish` 로그, DB 쓰기 권한 |
| 앱이 무한 폴링 | 타임아웃 미설정 | 앱 폴링 상한(예: 60s)·에러 처리 |

## 로그·상태 빠른 명령

```bash
CB="docker compose -f deploy/compose/compose.base.yml -f deploy/compose/compose.dev.yml --env-file deploy/env/.env"
$CB ps                          # 파트 상태
$CB logs -f gateway             # 특정 서비스
$CB logs -f worker engine-analysis engine-prescription
curl -s -H 'Host: api.localhost' http://localhost/health/db
curl -s -H 'Host: api.localhost' http://localhost/debug/engines   # dev
curl -s -H 'Host: api.localhost' http://localhost/jobs/<id>/events | python3 -m json.tool
```
구조적 로깅·알림·보존은 [`../../deploy/ops-jobs/`](../../deploy/ops-jobs/) (logging_config·alert·retention) 참조.

## 남은 결정 포인트 (막히지 않지만 확정 필요)

1. **종합 vs 지표별 처방 비율** — 대표 1개로 낼지, 지표별 다중으로 낼지.
2. **설문 문항·척도** — `survey.py` 매핑 확장(계약 유지).
3. **믹스 선택 로직** — 단일 지표 트리거 이상(조합/우선순위/상한)이 필요한지.
4. **PCR 매핑** — `pcr_to_mixes` 실제 마커→PM 코드 규칙.
