# SkinLens 프로젝트 분석 이야기 — 피부 진단소를 둘러보다

> 「서버 이야기」가 주방을 짓는 이야기였다면, 이 문서는 **완성된 가게를 둘러보는** 이야기입니다.
> 손님(고객)이 피부 사진 한 장을 올리면, 그 사진이 어떤 여정을 거쳐 "당신의 피부는 이렇습니다"라는 리포트가 되어 돌아오는지, 그리고 그 여정을 지키는 사람들이 어떻게 일하는지를 따라가 봅니다.
> 세부 기술 명세는 [`../ANALYSIS_REPORT_2026-08-19.md`](../ANALYSIS_REPORT_2026-08-19.md)에 있고, 여기선 그 **흐름과 의미**를 이야기로 잇습니다.

## 등장인물 (부품 ↔ 비유)

| 비유 | 실제 부품 |
|------|-----------|
| 피부 진단소 간판 | Vercel — 전 세계 어디서나 접속하는 웹사이트 |
| 손님이 보는 앱 | Next.js PWA — 스마트폰에 설치되는 피부 진단 앱 |

| 진단소 낙인 | Supabase JWT — 손님 신분을 확인하는 도장 |
| 예약 시스템 | Job Queue — 번호표를 뽑고 순서를 기다리는 시스템 |
| 응급 처치반 | deploy.sh — 문제 생기면 이전 상태로 되돌리는 비상 대응팀 |

## 막 1. 손님이 찾아오다 — 웹사이트와 앱

피부 진단소는 **두 개의 입구**가 있습니다.

하나는 **웹사이트**입니다. 누구나 브라우저로 `skinlens.example.com`에 접속하면, 피부 진단소의 간판이 보입니다. 이 간판은 **Vercel**이라는 전문 간판 제작소가 전 세계에 걸어줍니다. 한국에서 접속하든 미국에서 접속하든, 가장 가까운 간판을 보여주어 빠르게 열립니다.

다른 하나는 **스마트폰 앱**입니다. 손님이 앱을 설치하면, 홈 화면에 "SkinLens" 아이콘이 생깁니다. 이 앱은 **PWA(Progressive Web App)** 기술로 만들어져, 한 번 설치하면 오프라인에서도 기본 화면은 열립니다. 다만 사진을 올리거나 결과를 받는 기능은 인터넷이 필요합니다 — 민감한 피부 정보이기 때문에, 앱은 이 데이터를 **절대 캐시(저장)하지 않습니다** (PIPA 개인정볳호법 준수).

> **고객 관점에서**: 앱을 켜면 로그인 화면이 뜹니다. 카카오톡이나 구글 계정으로 간편 로그인하면, 진단소가 "이 손님이 맞습니다"라는 **낙인(Supabase JWT)**을 찍어줍니다. 이 낙인은 1시간마다 자동으로 갱신되어, 손님이 따로 로그인할 필요가 없습니다.

## 막 2. 사진을 올리다 — 접수와 보관

손님이 앱에서 "피부 분석 시작"을 누륵니다. 칠면조처럼 붉은 기가 있는 볼, 모공이 신경 쓰이는 코 — 스마트폰 치료로 찍은 사진 한 장을 선택합니다. 그리고 짧은 설문에 답합니다: "평소 피부가 민감한 편인가요?", "자주 트러블이 나나요?"

여기서 **마법 같은 일**이 벌어집니다. 사진은 진단소 서버를 **거치지 않고**, 곧바로 **사진 보관함(Supabase Storage)**으로 배송됩니다. 진단소 접수 데스크(gateway)는 "몇 번 보관함에 넣었습니다"라는 **쪽지(image_key)**만 받습니다.

> **왜 이렇게 할까요?** 피부 사진은 매우 민감한 개인정보입니다. 진단소 서버를 거치면 서버에 흔적이 남을 수 있습니다. 그래서 손님의 사진은 **직접 보관함으로** 본내고, 진단소는 "보관함 번호"만 알고 있는 구조입니다. 이것을 **presigned 업로드**라고 부릅니다.

물론 아무 사진이나 보관함에 들어갈 수는 없습니다. 접수 데스크가 미리 확인합니다:
- **사진 형식**: JPEG, PNG, WebP만 가능 (GIF나 HEIC는 불가)
- **사진 크기**: 최대 25MB (너무 크면 보관함이 거부)
- **도장 횟수**: 한 손님이 1분에 최대 10번까지만 사진을 올릴 수 있음 (남용 방지)

## 막 3. 번호표를 받다 — 비동기 처리의 마법

사진이 보관함에 들어가면, 접수 데스크는 손님에게 **번호표(job_id)**를 걷니다. "3번이십니다. 결과가 나오면 앱에서 알려드릴게요."

손님은 이제 **자유롭습니다**. 커피를 마시러 가도 되고, 다른 일을 봐도 됩니다. 진단소는 손님을 붙잡아 두지 않습니다. 이것이 **비동기 처리**의 핵심입니다 — 손님은 요청만 하고, 결과는 나중에 확인합니다.

번호표에는 마법이 걸려 있습니다. 이 번호로는:
- 지금 진단이 진행 중인지 알 수 있습니다 (`GET /jobs/{id}`)
- 어떤 단계를 거쳤는지 볼 수 있습니다 (`GET /jobs/{id}/events`)
- 최종 결과를 받을 수 있습니다 (진단 완료 시)

## 막 4. 뒤에서 진단하다 — 진단 보조의 하루

손님이 커피를 마시는 동안, 진단소 뒤에서는 **진단 보조(worker)**가 바쁘게 움직입니다.

진단 보조는 **예약 시스템(Job Queue)**을 쳐다봅니다. "3번 손님, 사진 도착했습니다." 예약 시스템은 **Postgres**라는 특수한 장부를 사용하는데, 여러 진단 보조가 동시에 일핵도 같은 손님을 중복 처리하지 않도록 **SKIP LOCKED**라는 마법 주문이 걸려 있습니다.

진단 보조의 하루는 이렇습니다:

1. **사진 수거**: 보관함에서 3번 손님의 사진을 꺼냅니다. 이때 **포장 검수**를 합니다 — 상자 안이 진짜 사진인지, 가짜 사진(악성 파일)은 아닌지 **magic-byte**라는 지문을 확인합니다.

2. **진단실 1 방문**: 사진을 **진단실 1(engine-analysis)**에 가져갑니다. 이 방은 창문이 없습니다(폐쇄망). 외부와 완전히 차단되어, 사진이 밖으로 새어나갈 수 없습니다. 진단실 1에서는 **OpenCV**라는 특수 치료로 사진을 찍어, 피부의 10가지 지표를 측정합니다: 지성, 건성, 복합성, 민감성, 트러블, 색소·톤, 모공, 피부결, 주름·탄력, 붉은기.

3. **진단실 2 방문**: 진단실 1의 결과지와 손님의 설문지를 함께 **진단실 2(engine-prescription)**에 가져갑니다. 이 방도 창문이 없습니다. 진단실 2에서는 종합 점수를 매기고, "이 손님은 '경미' 등급이므로 0.5% 처방 비율이 적합합니다"라고 결론 내립니다. 그리고 M01~M11 중에서 적합한 **믹스(화장품 조합)**를 고릅니다.

4. **기록 정리**: 두 진단실의 결과를 **진단 기록부(Supabase Postgres)**에 정리합니다. "3번 손님: 분석 완료(점수 68), 처방 완료(등급 경미, 비율 0.5%, 선택 믹스 M03+M07)"라고 기록하고, "완료" 도장을 찍습니다.

> **안전 장치**: 진단 보조가 실수로 같은 손님을 두 번 처리핳도, 기록부는 **ON CONFLICT DO NOTHING**이라는 마법으로 중복 기록을 막습니다. 그리고 진단실이 고장 나면 최대 3번까지 다시 시도하고, 그래도 안 되면 "진단 불가"라고 손님에게 알립니다.

## 막 5. 결과를 받다 — 리포트의 탄생

커피를 다 마신 손님이 앱을 열어봅니다. "3번 손님, 진단이 완료되었습니다."

앱 화면에는 **10가지 지표**가 그래프로 보입니다:
- 지성: 72점 (양호)
- 건성: 45점 (보통)
- 민감성: 58점 (경미)
- 트러블: 65점 (양호)
- ...

그리고 **종합 점수 68점**과 **등급: 경미**가 표시됩니다. "현재 피부 상태는 전반적으로 양호하나, 건조함과 민감함이 약간 있습니다. 0.5% 농도의 처방을 권장합니다."

아래에는 **맞춤 믹스**가 나옵니다: "M03(수분 공급) + M07(진정 케어)를 기본으로 하되, 색소 침착이 신경 쓰이시면 PM01(브라이트닝)을 추가하세요."

이 모든 정보는 진단 기록부에서 가져온 것이며, 손님 본인만 볼 수 있습니다. 다른 손님의 정보는 절대 볼 수 없습니다 — **RLS(Row Level Security)**라는 마법이 "본인 기록만 열어볼 수 있음"을 강제합니다.

## 막 6. 진단소를 지키다 — 보안과 안정성

피부 진단소는 **민감한 개인정보**를 다루므로, 보안이 생명입니다.

### 6.1 신분 확인 (인증)

- **손님**: 카카오/구글 로그인 → Supabase가 JWT 발급
- **진단소 직원**: service_role 키 → RLS 우회 (관리 목적)
- **진단실**: 아무 키도 없음 — 외부와 완전 차단 (Case A 격리)

### 6.2 사진 보호 (심층 방어)

1. **접수 데스크**: 파일 형식·크기 검증
2. **보관함**: 25MB 상한, 허용 형식만 저장
3. **진단 보조**: magic-byte 재검증 (가짜 사진 차단)
4. **전송**: HTTPS 암호화

### 6.3 장부 보호 (RLS)

- 모든 손님 기록은 `user_id = auth.uid()` 정책으로 본인만 조회
- `job_events`도 상위 `jobs` 소유권으로 연결하여 보호
- 보관함 사진도 `(storage.foldername(name))[1] = auth.uid()`로 소유자만 접근

### 6.4 응급 대응 (롤백)

진단소에 새로운 진단 기계를 들였는데 고장 났습니다. **응급 처치반(deploy.sh)**이 출동합니다:
1. 새 기계의 태그를 기록부에 적습니다
2. 기계를 켜고 120초간 상태를 지켜봅니다
3. 이상이 없으면 정상 가동
4. 이상이 있으면 **자동으로 이전 기계로 되돌립니다** (롤백)

## 막 7. 진단소의 하루 — 운영과 관리

### 아침 (자동 개점)

진단소는 아침에 자동으로 문을 엽니다(`restart: unless-stopped`). Docker라는 규격화된 조리대가 모든 기계를 켜고, 상태 점검(healthcheck)으로 "진단실 1, 정상", "진단실 2, 정상"을 확인합니다.

### 낮 (정상 영업)

손님들이 오고 갑니다. 진단 보조는 바쁘게 사진을 옮기고, 접수 데스크는 번호표를 나눠줍니다. 모든 기록은 **구조적 JSON 로깅**으로 남아, 나중에 "3번 손님의 사진이 어디서 멈췄지?"라고 추적할 수 있습니다.

### 밤 (정리와 백업)

영업이 끝나면:
- **로그 정리**: 오래된 로그는 자동으로 지워집니다 (최대 10MB × 3개)
- **장부 백업**: `pg_backup.sh`가 진단 기록부를 AES-256으로 암호화하여 안전한 곳에 보관합니다
- **보존 정리**: `retention.py`가 완료된 진단의 원본 사진을 정리합니다 (공간 확보)

### 주말 (점검과 리허설)

- **복구 리허설**: `restore-rehearsal.sh`가 "만약 장부가 날아가면?"을 가정하고 복구 연습을 합니다 (RPO/RTO 측정)
- **보안 점검**: `log-scrub.py`가 로그에서 민감정보(토큰, URL)를 마스킹합니다

## 막 8. 진단소의 미래 — 3-Tier로의 진화

피부 진단소는 원래 **한 지붕 아래** 모든 것이 있었습니다. 웹사이트, 데이터베이스, 진단실이 모두 같은 건물에 있었습니다. 그런데 손님이 늘어나자 문제가 생겼습니다:
- 웹사이트가 느려짐 (전 세계 손님이 몰림)
- 데이터베이스 용량 부족
- 진단실 GPU 부족

그래서 **3-Tier로 이사**를 결정했습니다:

```
이전: 한 지붕 아래
┌─────────────────────────┐
│  웹사이트 + DB + 진단실  │
│      (모두 한 곳에)      │
└─────────────────────────┘

이후: 전문점 셋
┌─────────┐  ┌─────────┐  ┌─────────┐
│ 쇼윈도   │  │ 데이터   │  │ 우리     │
│(Vercel) │  │ 창고     │  │ 주방     │
│         │  │(Supabase)│  │(AI Server)│
│ Next.js │  │ Postgres │  │ gateway │
│   PWA   │  │ Storage  │  │ worker  │
│         │  │   Auth   │  │ engine-*│
└─────────┘  └─────────┘  └─────────┘
```

**현재 상태**:
- ✅ 쇼윈도(Next.js PWA) — 코드 완료, Vercel 연결 준비 중
- ✅ 데이터 창고(Supabase) — 코드 완료, 프로젝트 생성·실제 연결 준비 중
- ✅ 우리 주방(AI Server) — 코드 완료, 운영 중

## 막 9. 고객이 알아야 할 것들

### Q: 내 사진은 안전한가요?

**A**: 네, 매우 안전합니다.
- 사진은 진단소 서버를 거치지 않고 곧바로 보관함으로 갑니다
- 보관함은 25MB 상한과 형식 검증으로 가짜 파일을 막습니다
- 진단 보조가 magic-byte로 한 번 더 검증합니다
- RLS로 본인만 사진을 볼 수 있습니다
- HTTPS로 전송 중 암호화됩니다

### Q: 결과는 얼마나 걸리나요?

**A**: 보통 **10~30초**입니다.
- 사진 업로드: 3~5초
- 진단실 1(분석): 5~10초
- 진단실 2(처방): 2~5초
- 기록 정리: 1~2초

네트워크 상태와 사진 크기에 따라 달라질 수 있습니다.

### Q: 내 정보는 누가 볼 수 있나요?

**A**: **오직 본인만** 볼 수 있습니다.
- 진단소 직원(관리자)도 service_role 키로 접근할 수 있지만, 이는 엄격히 통제됩니다
- 다른 손님은 절대 볼 수 없습니다 (RLS 강제)
- 진단실(engine-*)은 아예 외부와 차단되어 있습니다

### Q: 앱을 지우면 기록도 사라지나요?

**A**: 아니요. 기록은 **진단 기록부(Supabase)**에 남습니다.
- 앱을 지워도 웹사이트에서 로그인하면 같은 기록을 볼 수 있습니다
- 완전히 삭제하려면 진단소에 요청해야 합니다 (GDPR/PIPA 삭제권)

### Q: 오류가 나면 어떻게 하나요?

**A**: 진단소는 **자동 복구** 시스템이 있습니다.
- 진단실 고장: 최대 3번 자동 재시도
- 시스템 오류: 응급 처치반이 자동으로 이전 상태로 복구
- 그래도 안 되면: "진단 불가" 상태로 표시되고, 진단소에 문의하시면 됩니다

## 마치며

피부 진단소는 **"손님의 피부를 정확히 진단하고, 안전하게 기록하고, 빠르게 결과를 전달한다"**는 단 하나의 목표로 설계되었습니다.

그 목표를 위해:
- **3-Tier 아키텍처**로 각 계층을 전문화했습니다
- **presigned 업로드**로 민감정보를 보호했습니다
- **심층 방어**로 보안을 다중화했습니다
- **비동기 처리**로 사용자 경험을 최적화했습니다
- **자동 롤백**으로 서비스 안정성을 확보했습니다

이제 남은 것은 **실제 세상과의 연결**입니다. Supabase 프로젝트를 생성하고, Vercel에 웹사이트를 올리고, 실제 손님을 받는 일입니다. 기술적 준비는 모두 끝났습니다.
